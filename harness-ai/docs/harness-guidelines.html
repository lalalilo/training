Start Here — what is a "harness"?

A harness is the safety setup around the AI

Think of an AI coding assistant like a very fast new hire who has never seen your codebase. A harness is everything you put around that assistant so it does good work without breaking things: the written rules it reads, the automatic checks that stop it from doing something dangerous, and the tests that prove its work is correct. The AI model is the engine; the harness is the seatbelts, guardrails, and dashboard.

Why it matters

  • AI is confident even when wrong — it needs checking, not trust
  • A monorepo has many apps — one careless change can hit code you didn't mean to touch
  • Real customers use this code — "looks done" is not the same as "is correct"

Two words you'll see a lot

Deterministic

A check that always runs the same way, like a script — it can't be talked out of it. Reliable.

Advisory

A written instruction the AI may or may not follow, like a note in a doc. Helpful, but not a guarantee.

The Core Idea

The harness is the product

An AI model guesses the next best answer — it's often right, but never guaranteed. You don't make it safe by trusting it; you make it safe with automatic layers around it that constrain, check, and stack up. Each layer is cheap; together they're a guardrail system.

"AI tools amplify existing expertise." — Simon Willison, vibe engineering, Oct 2025

Principle 1 — Layered defense

Eight layers, lowest friction first

No single check catches everything, so you stack cheap layers — like slices of swiss cheese, where one slice's holes are covered by the next. Green layers are automatic (they always fire); blue layers are notes the AI reads (it might skip them). Put your scariest risks in the green layers.

2Rules — .claude/rules/Extra context loaded automatically for a given area of code
3SkillsSaved step-by-step recipes for tasks the AI does often
4Sub-agentsHelper AIs with a narrow job and limited tools

Principle 2 — Deterministic beats advisory

Put the top risks where the model can't forget

Two ways to make the AI do something. A deterministic check is a script that runs automatically and always behaves the same — the AI can't skip it. An advisory instruction is just written guidance (e.g. a line in a docs file) the AI might follow — but in a long session it loses track of earlier instructions (called "context rot"), so guidance gets forgotten. Lesson: don't put critical safety in writing the AI can ignore — put it in a script it can't.

✅ Deterministic — automatic, reliable

  • Hooks — a script that blocks the action; runs no matter what
    .claude/hooks/*.sh + .claude/settings.json
  • Required CI checks — build/test/lint must pass before merge
    .github/workflows/ · .circleci/config.yml
  • Permission deny-list — forbidden commands, can't be overridden
    .claude/settings.json → permissions.deny
  • Git pre-commit hook — rejects bad commits before they exist
    .husky/pre-commit

⚠️ Advisory — guidance, may be ignored

  • Instructions / rules the AI reads — influence what it tries, don't stop it
    CLAUDE.md · .claude/rules/*.md
  • "Remember to run the tests" — works early, forgotten once the session gets long
    a line inside CLAUDE.md
  • Coding-style notes in prose — followed at first, then slowly drift
    CLAUDE.md / README prose

Adaptive attacks beat 12 published prompt-injection defenses >90% despite ~0% in their papers. Don't rely on the model behaving. — Willison, Nov 2025

What makes a CI check "required"? The workflow file (.github/workflows/) only defines what runs — by itself an agent could still merge a failing PR. The check becomes mandatory via branch protection, a setting on the GitHub/GitLab server (not in the repo) that disables the merge button until the check passes and forbids direct pushes to main. The agent can't edit that server setting and has no merge-bypass — so its only path to main is through the gate.
Principle 3 — Verification substitutes for reading

"Don't read the code" is earned, never free

A growing trend: some well-known engineers let the AI write code they barely read. That only works because they have strong automatic tests and checks proving the code behaves correctly — they trust the results, not the AI. Without those checks it's just gambling. The quotes below are practitioners describing the trade-off honestly.
"Test at the right boundaries and you can ignore what's inside… every change should trigger your pre-commit hooks, CI, and type checking."
Matt Pocock — grey-box modules · Mar 2026
"I'm not reviewing every line… even for my production stuff." — then names it normalization of deviance.
Simon Willison · May 2026
"I certainly haven't. No time for field trips." — but The Mayor agent reviews every PR.
Steve Yegge · Mar 2026

The deal you're making

You stop reading every line and instead trust that automated checks prove the code behaves correctly. That trade is only safe when those checks are real and strong.

The test: could you confidently let the AI's change ship without reading it? Only if a failing check would have caught it. If not — you're gambling, so read it.

The exact checks that earn this trust — tests written first, type checking, a second AI reviewing the diff, running it for real — are Principle 5, stage 2 (“prove it works”). This slide is the why; that one is the how.

Trust the checks, not the AI. Nobody safe stopped reading code and replaced it with nothing.

Principle 4 — Know the real risks first

What actually goes wrong — four documented cases (among many)

The danger isn't only buggy code — it's an agent with too much access getting tricked. These are documented, real exploits, not hypotheticals. Read them first; the very next slide (Principle 5) shows the workflow that prevents each one.

CASE A ☠️ Data leak via the "lethal trifecta"

The dangerous combo is one agent that has all three: (1) access to private data, (2) exposure to content from outside, (3) a way to send data out.

GitHub MCP, May 2025: a user asked their Claude agent to "look at the open issues" in a public repo. One issue was a trap: it told the agent to read the user's private repos and paste their contents into a public pull request. The agent obeyed — private code leaked, no human action needed.

Source: invariantlabs.ai/blog/mcp-github-vulnerability · term: simonwillison.net (Jun 2025)

CASE B 🔑 Stolen credentials

If the agent can be tricked and it holds real keys, the attacker gets your keys' powers too — reading or exfiltrating whatever those credentials unlock.

GitLab Duo, May 2025: a hidden instruction in a public merge request made the AI use its access to grab a private project's source, base64-encode it, and smuggle it out inside an image URL in its own reply.

Source: legitsecurity.com — GitLab Duo prompt injection

CASE C 📦 Poisoned dependencies ("slopsquatting")

AI sometimes invents a package name that doesn't exist; an attacker registers that exact name with malware. The agent then installs the attacker's code.

Lasso Security, 2024: researchers registered huggingface-cli, a package name GPT models kept hallucinating. It got 30,000+ real downloads in 3 months — even Alibaba's docs told people to install it.

Source: lasso.security/blog/ai-package-hallucinations · OWASP LLM03:2025

CASE D 🐛 Plausible-but-broken code

The quiet one: the AI writes code that looks right, reads well, and even runs — but is subtly wrong, mishandles an edge case, or breaks something elsewhere. No attacker needed.

Everyday reality: "looks done" is not "is correct". Without checks that actually exercise the behaviour, these slip through review and surface in production in front of customers.

Source: simonwillison.net — vibe coding

Principle 5 — A workflow that prevents all four

Three stages, in order: write → prove → ship

Each CASE badge below matches the same badge on the previous slide — that's the stage that stops it. Getting AI to write code is the easy part; proving it's correct and shipping it safely are what make it OK for real customers. Skip a stage and the matching risk comes back.
1 · WRITE IT
The AI writes code, guided and fenced in.
It reads your CLAUDE.md and .claude/rules/ for how this repo works.
A PreToolUse hook blocks dangerous commands (migrate down, kubectl delete).
CASE A Scope its access: never give one agent private data + outside input + a way out at once.
CASE B It holds no real secrets; CI uses short-lived OIDC tokens.
Works in a git worktree — an experiment can't touch your main checkout.
→
2 · PROVE IT WORKS
Evidence the code is correct — not "looks fine".
CASE D yarn test + check-types on every change; broken behaviour turns a test red.
Run the real feature end-to-end (e.g. a Playwright script clicking through it).
A second AI reviews the diff in a fresh chat (claude-pr-review) and tries to break it.
CASE C yarn audit + lockfile review before merge.
Track rework rate — how often merged AI code has to be fixed afterwards.
→
3 · SHIP IT SAFELY
Roll out so a bad change is caught or undone fast.
Open a Pull Request; branch protection forbids pushing straight to main.
Required CI checks (GitHub Actions / CircleCI) must be green before the merge button unlocks.
Release behind a feature flag or to a small % of users first (canary), not everyone at once.
If metrics spike, roll back in one click — revert the merge / flip the flag off.

Green = "looks done". Amber = "proven done". Red = "safe in front of customers". All three, in order.

Principle 6 — Make it efficient & self-improving

Make it fast to use, and let it improve itself

A safe harness that's painful to use gets bypassed. Two goals here: remove friction so the AI runs smoothly, and measure the right things so you can tell if AI work is actually helping — not just producing more code.

⚡ Make it efficient

  • Pre-approve safe commands — agent runs without nagging for permission; only stops at genuinely risky actions
  • Write it once, reuse everywhere — shared rules at the root; a new app inherits the whole harness for free
  • Let agents do the chores — scheduled jobs that simplify code / clear tech debt, and undo themselves if they break a build
  • Self-improving loop — a weekly "gardener" agent audits the code & the harness itself and files a few fix tickets

📊 Measure the right thing

  • Rework rate — how often AI code passes review but has to be fixed later. Rising = trouble. The best early warning.
  • First-pass acceptance — % of AI changes merged with no edits. A real quality signal — unlike "lines of code", which rewards volume.
  • Failure rate & time-to-recover — how often a change breaks production and how fast you fix it, tracked separately for AI vs human work

Watch out: measuring volume (lines, PR count) hides the real cost — more code = more to maintain. — ThoughtWorks Radar 34
